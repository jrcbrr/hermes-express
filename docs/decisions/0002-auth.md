# ADR 0002: Authentication and authorization

- **Status:** Accepted
- **Date:** 2026-10-29
- **Stage:** 2 (auth)

## Context

Customers need accounts to order, track orders, save favorites and earn points. Staff need roles: a **barista** works one branch's queue, an **admin** manages everything (docs/PLAN.md §8). The app runs on Vercel serverless functions with Neon Postgres, and Next.js 16 has Cache Components (Partial Prerendering) turned on.

Requirements:

- Email + password sign-up and login, with passwords hashed and never stored in plain text.
- Roles that users cannot give themselves.
- Protected pages (checkout, orders, favorites, rewards, profile, `/barista/**`, `/admin/**`).
- Rate limiting on auth so passwords can't be guessed quickly.
- No paid third-party service, and user data stays in our own database.

## Decision

1. **Better Auth** with its **Drizzle adapter** on Neon. Sessions are rows in the `session` table, referenced by an HTTP-only cookie. Passwords are hashed with scrypt.
2. **Extra user fields** (`phone`, `role`, `branchId`, `pointsBalance`, `defaultAddress`) are Better Auth `additionalFields`. `role`, `branchId`, `pointsBalance` and `defaultAddress` are `input: false`, so a sign-up request cannot set them. Roles are only changed by the seed script now, and by admins later (Stage 7).
3. **Forms use server actions** (`src/server/auth/actions.ts`), not Better Auth's browser client. Each action validates with Zod, checks the rate limit, then calls `auth.api.*` on the server. The `nextCookies` plugin lets the action set the session cookie. The forms work without JavaScript, and validation messages are ours (formal and friendly).
4. **Two layers of protection:**
   - `src/proxy.ts` (Next.js 16's new name for middleware) does a fast **cookie-only** check: no session cookie on a protected path → redirect to `/login?next=…`. It doesn't touch the database.
   - `requireUser()` / `requireRole()` in `src/server/auth/session.ts` do the **real** check (session from the database, then role) in every protected page and server action. The proxy alone is not trusted: a cookie can be stale or forged, and it says nothing about the role.
5. **Route rules live in one pure module**, `src/lib/roles.ts`, shared by the proxy, the server helpers and the account menu.
6. **Rate limiting in Postgres.** One `rate_limit` table and one atomic upsert (`src/server/rate-limit.ts`). It backs both our server actions (5 attempts per minute per IP for sign-up; per IP and per email for login) and Better Auth's own `/api/auth/*` limiter (through `customStorage`). In-memory limits don't work on serverless, because each instance would have its own counter.
7. **Base URL:** `BETTER_AUTH_URL` in production. On Vercel previews it falls back to `https://$VERCEL_URL`, and both preview aliases are trusted origins.

## Alternatives considered

| Option                | Why not                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| Auth.js (NextAuth)    | Credentials login is discouraged and session handling for it is awkward; custom fields need more work. |
| Clerk / Auth0         | Hosted and paid beyond a free tier; user data lives outside our database; less to learn from.          |
| Hand-rolled sessions  | Easy to get security details wrong (hashing, cookie flags, timing attacks).                            |
| JWT-only sessions     | Can't be revoked on logout without extra work; database sessions are simple with Neon.                 |
| Upstash Redis limiter | Another service and secret to manage; Postgres is already there and fast enough for auth traffic.      |

## Consequences

**Good**

- Users, sessions and roles live in our Postgres, typed end to end with Drizzle.
- Security-critical checks are on the server and unit tested (`roles.ts` 100%, `session.ts`, `actions.ts`).
- Pages keep their static shell: only the account area and protected content read the session, inside `<Suspense>`.

**Trade-offs**

- Two protection layers must stay in sync. A unit test checks that the proxy matcher covers every protected prefix in `roles.ts`.
- The Neon HTTP driver has no transactions, so the seed script repairs a half-created staff account if it is re-run.
- The rate limiter trusts `x-forwarded-for`. On Vercel this header is set by the platform; self-hosting behind another proxy would need a review.
- Email verification and password reset are not in scope yet (no email until Stage 8).
